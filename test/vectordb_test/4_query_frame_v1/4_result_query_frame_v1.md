# 4_query_frame_v1 — Semantic Query Frame v1 검증 결과 보고서

## 1. 목적과 결론

이 실험은 에이전트 파이프라인 1단계인 **Semantic Query Frame Extraction**이 자연어 금융상품 질의를 구조화하면서 다음 계약을 지키는지 검증한다.

1. 항상 파싱 가능한 고정 스키마를 출력하는가
2. 질문에 필요한 슬롯은 빠뜨리지 않고, 필요 없는 슬롯은 만들지 않는가
3. 연산자·값·단위·시점처럼 실행 결과를 바꾸는 의미를 보존하는가
4. 검증이 필요한 질의와 모호한 표현을 안전하게 표시하는가
5. 추출 프레임이 다음 단계의 TBox 검색에 실제로 도움이 되는가

평가 결과, **v1은 전 항목 통과 기준에는 미달**했다. 다만 구조 유효성과 핵심 의미 보존은 강했고, 모호한 표현을 임의로 확정하지 않는 안전 속성도 확인됐다.

- 강점: JSON 파싱 35/35, 보정 전 스키마 준수 35/35, `operator`·`unit`·`temporal` 100%, 모호 질의의 Premature Resolution 0/12
- 약점: `constraints` Recall/Precision 75.8%/78.1%, `computation` Recall 50.0%, `relation` 양끝 Exact 50.0%, validation 유형 정확도 60.0%
- 검색 결론: 프레임만으로 원문을 대체하면 성능이 하락한다. 원문 결과에 슬롯별 검색을 합치는 `A+B′`가 운영 지점 `K=5`에서 R@5를 13.1%에서 15.8%로 높였다.
- 운영 결론: 정확도가 확인된 슬롯만 계약값으로 사용하고, 나머지는 Planner의 힌트로만 사용해야 한다.

측정일은 **2026-08-23**, 추출 모델은 **HyperCLOVA X HCX-007**, 스키마 버전은 결과 파일 기준 `v1-draft`다.

### 2.1 평가셋

- 본 평가: 예상 평가 질문 35문항
- 모호성 안전성 평가: 본 평가와 별도로 만든 12문항
- 모델 사전 선별: 조회·조건·관계·검증을 대표하는 4문항
- Downstream 검색: 35문항의 gold TBox concept 중 평가 인덱스에 실제 존재하는 concept

35문항에는 데이터 부재로 최종 답변이 불가능한 q014·q023·q025·q030도 포함한다. 이 실험은 **질문 이해 단계**를 평가하므로, 데이터가 없어도 의도 프레임 자체는 정상 추출해야 한다. 데이터 부재는 실행 단계에서 판정하며 `validation_targets`의 5개 ABSTAIN 유형과 섞지 않는다.

### 2.2 출력 계약

주요 슬롯은 `domain_candidates`, `task`, `targets`, `entities`, `constraints`, `relations`, `ordering`, `limit`, `temporal`, `computation`, `ambiguity`, `validation_targets`다.

확정한 설계 결정은 다음과 같다.


| ID  | 결정                                                        | 이유                                                             |
| --- | --------------------------------------------------------- | -------------------------------------------------------------- |
| D1  | `domain_candidates`는 `bond_kr/etf_kr/etf_gl/fund_pub`의 배열 | 복합 도메인 7문항과 국내·해외 ETF 구분을 보존하기 위해서다.                           |
| D2  | ABSTAIN 코드는 `ABSTAIN_INVALID_TAXONOMY` 같은 긴 형식을 정본으로 사용   | 평가 문자열과 TTL 주석의 표기를 통일한다.                                      |

### 2.3 평가셋 오염 통제

평가 문항의 답을 프롬프트가 직접 암기하지 않도록 다음 겹침을 제거했다.

- q013과 동일했던 few-shot 원문을 평가셋에 없는 가상 질의로 교체
- `AA- 이상`, `순자산 1조 원 이상`, `총보수 0.05% 이하`, `잔존기간 3년 이하` 예시를 각각 `A+`, `2조 원`, `0.20%`, `듀레이션 4년`으로 교체
- q031과 같은 `신용등급 AAAA` 예시를 `위험등급 9등급`으로 교체

남아 있는 `신용등급`, `총보수`, `편입증권` 등은 출력 필드의 의미를 설명하는 도메인 어휘이지 정답 예시는 아니다.

단, 별도 감사 프롬프트에는 `AAA가 최상단`이라는 규칙과 `발행은 기업·기관이 하는 일`이라는 규칙이 들어 있다. 따라서 q031과 q035의 validation 성능은 **완전한 사전지식 비주입 결과가 아니며**, 이 두 규칙의 도움을 받은 결과로 해석해야 한다.

## 3. 측정 방법과 지표 정의

### 3.1 왜 채움률을 정확도로 사용하지 않는가

`entities 22/35` 같은 채움률은 품질을 뜻하지 않는다. 엔티티가 필요 없는 질문이 13개라면 낮은 채움률이 오히려 정답일 수 있다. 따라서 gold 값이 비어 있지 않으면 **REQUIRED**, 비어 있으면 **NOT REQUIRED**로 파생하고 다음을 측정한다.

- True Positive(`TP`): gold에 필요한 항목을 예측에서도 올바르게 생성
- False Negative(`FN`, 누락): gold에는 있지만 예측하지 못한 항목
- False Positive(`FP`, 오생성): gold에 없거나 다른 항목을 불필요하게 생성
- Recall = `TP / gold 항목 수 = TP / (TP + FN)`
- Precision = `TP / pred 항목 수 = TP / (TP + FP)`

별도 `applicable` 필드를 두지 않으며, 빈 gold에 예측이 생기면 그대로 FP가 된다. 보고서의 슬롯 Recall·Precision은 문항별 평균이 아니라 **35문항 전체 항목을 합산한 micro 지표**다.

### 3.2 텍스트 슬롯의 매칭 규칙

한국어 표현 차이 때문에 단순 문자열 exact match만 사용하지 않는다.

1. 공백과 괄호·따옴표·가운뎃점 등 일부 문장부호를 제거하고 소문자화한다.
2. gold는 복수 별칭을 허용한다.
3. gold와 pred를 완전일치 우선으로 1:1 매칭한다.
4. 남은 항목은 길이 2자 이상일 때 포함 관계로 1:1 매칭한다.
5. 한 예측을 여러 gold 정답의 TP로 중복 계산하지 않는다.

`targets`, `entities`, `constraints.field_text`, `ordering.field_text`에 이 규칙을 적용한다. `relations`는 경로 표현의 변동성이 커서 우선 관계의 존재 여부만 Recall·Precision으로 평가하고, 경로의 첫·마지막 개체는 별도 Exact 지표로 평가한다.

### 3.3 Exact 지표

`task`, `limit`, `temporal.kind`처럼 단일값인 슬롯은 `정답 수 / 평가 대상 수`로 계산한다. `operator`, `value`, `unit`, `entity role`, `sort direction`은 상위 텍스트 항목이 gold와 1:1로 대응된 경우에만 의미 보존을 평가한다.

따라서 예를 들어 `operator 25/25`는 35문항 전체의 모든 조건을 의미하지 않는다. `constraints.field_text` 매칭에 성공한 25개 조건에서 연산자가 모두 맞았다는 뜻이다. 조건 자체가 누락된 8개는 `constraints` Recall에서 이미 벌점을 받으며 `operator` 분모에는 다시 넣지 않는다.

### 3.4 통과 기준


| 평가 영역      | 통과 기준                                        | 기준의 의미                                 |
| ---------- | -------------------------------------------- | -------------------------------------- |
| 구조 유효성     | 35/35 JSON 파싱, 35/35 보정 전 스키마 준수, TBox 누출 0건 | 모든 문항이 후속 코드에서 안전하게 소비 가능해야 한다.        |
| 슬롯 정확도     | 각 슬롯 Recall과 Precision 모두 95% 이상             | 필요한 정보의 누락과 불필요한 생성 모두 제한한다.           |
| 의미 보존      | `operator` 100%, 나머지 95% 이상                  | 연산자 반전은 결과 집합을 뒤집으므로 한 건도 허용하지 않는다.    |
| validation | 대상 5/5 검출, 정상 30문항 FP 0건, 유형도 5/5 일치         | 위험 질의 누락과 정상 질의의 불필요한 기각을 모두 금지한다.     |
| 모호성        | Recall 12/12, Premature Resolution 0/12      | 모호 표현을 모두 표시하되 임의의 수치나 기준으로 확정하지 않는다.  |
| Downstream | 프레임 기반 최선안이 원문 기준선 이상                        | Query Frame이 실제 TBox 검색을 악화시키지 않아야 한다. |


95% 기준에서 표본 수가 작은 슬롯은 한 건 오류만으로도 크게 하락한다. 이 평가는 통계적 신뢰구간을 추정한 실험이 아니라 **35개 고정 계약 테스트의 합격 여부**를 보는 방식이다.

## 4. 모델 선택 실험

전체 평가 전에 대표 4문항으로 HCX-007, HCX-005, HCX-DASH-002를 비교했다. 여기서 `스키마 준수`는 guard 적용 전 원본이 필수 필드·enum·자료형 제약을 지켰는지, `guard 보정`은 후처리 규칙이 수정한 항목 수를 뜻한다.


| 모델           | 보정 전 스키마 준수 | guard 보정 | 관찰된 특성                       | 선택     |
| ------------ | -----------: | --------: | ---------------------------- | ------ |
| **HCX-007**  | **4/4**     | **1건**   | 대표 네 유형 모두 구조 계약 준수          | **채택** |
| HCX-005      | 2/4         | 6건       | 최대 12.6초로 가장 느림              | 제외     |
| HCX-DASH-002 | 1/4         | 10건      | domain 누락, 관계 질의를 조건검색으로 오분류 | 제외     |


- 이 비교는 **4문항 사전 선별 실험**이므로 모델의 일반 성능 순위를 확정하는 자료는 아니다.

- 다만 동일 프롬프트·동일 대표 유형에서 HCX-007이 구조 안정성과 후처리 의존도 모두 가장 좋았기 때문에 35문항 본 평가 모델로 선택했다.
- HCX-DASH-002의 과거 0.29초 측정치는 이번 긴 프롬프트에서 재현되지 않았다. 출력 토큰 생성 시간이 지연을 지배해 속도 이점이 사라졌고, 품질 차이를 상쇄하지 못했다.

## 5. 영역별 상세 결과

### 5.1 영역 1 — 구조 유효성과 계층 책임


| 항목            | 측정 기준                                            | 결과    | 판정   | 의미                                                                     |
| ------------- | ------------------------------------------------ | -----: | ---- | ---------------------------------------------------------------------- |
| JSON parse 성공 | 35개 응답을 JSON 객체로 복원 가능                           | 35/35 | PASS | 파싱 실패로 전체 파이프라인이 중단된 문항이 없다.                                           |
| 스키마 준수(보정 전)  | `_raw`가 필수 필드, enum, 중첩 객체, 수치형, `limit` 자료형을 준수 | 35/35 | PASS | guard가 잘못된 구조를 숨긴 결과가 아니라 모델 원출력이 계약을 지켰다.                             |
| TBox 누출       | 자연어 슬롯에서 `fp:` URI·물리 컬럼명·식별자형 경로 생성 여부          | 1건    | FAIL | q027이 `relations.path`에 `included_in`, `parent_company`를 생성해 D4를 위반했다. |


TBox 누출 검사는 `task` 같은 enum 필드는 제외하고 targets·entities·constraints·relations·ordering·temporal 등 자연어 슬롯을 검사한다. 1단계는 아직 TBox를 보지 않으므로, 이 단계에서 스키마 식별자를 만들어내면 존재하지 않는 관계를 후속 단계가 사실처럼 신뢰할 위험이 있다.

### 5.2 영역 2 — Applicability-aware 슬롯 정확도


| 슬롯                     | gold | pred | TP  | 누락(FN) | 오생성(FP) | Recall | Precision | 기준       | 판정      |
| ---------------------- | ----: | ----: | ---: | ------: | -------: | ------: | ---------: | --------: | ------- |
| domain_candidates      | 46   | 43   | 41  | 5      | 2       | 89.1%  | 95.3%     | R·P ≥95% | FAIL(R) |
| targets                | 39   | 41   | 37  | 2      | 4       | 94.9%  | 90.2%     | R·P ≥95% | FAIL    |
| entities               | 31   | 28   | 27  | 4      | 1       | 87.1%  | 96.4%     | R·P ≥95% | FAIL(R) |
| constraints            | 33   | 32   | 25  | 8      | 7       | 75.8%  | 78.1%     | R·P ≥95% | FAIL    |
| relations(존재)          | 11   | 11   | 10  | 1      | 1       | 90.9%  | 90.9%     | R·P ≥95% | FAIL    |
| ordering               | 7    | 6    | 6   | 1      | 0       | 85.7%  | 100%      | R·P ≥95% | FAIL(R) |
| computation(유형)        | 10   | 6    | 5   | 5      | 1       | 50.0%  | 83.3%     | R·P ≥95% | FAIL    |
| ambiguity(유형)          | 2    | 4    | 2   | 0      | 2       | 100%   | 50.0%     | R·P ≥95% | FAIL(P) |
| validation_targets(유형) | 5    | 5    | 3   | 2      | 2       | 60.0%  | 60.0%     | R·P ≥95% | FAIL    |


슬롯별 해석은 다음과 같다.

- `domain_candidates`: 예측한 도메인의 정확성은 95.3%로 기준을 넘었지만 필요한 도메인 5개를 놓쳤다. 특히 복합·세부 도메인 회수 성능이 부족하다.
- `targets`: 필요한 대상 표현은 2개만 누락했으나 4개를 불필요하게 분리하거나 생성했다. Recall 94.9%도 엄격 기준에 0.1%p 못 미친다.
- `entities`: 예측한 엔티티 텍스트는 비교적 정확하지만 4개를 놓쳤다. 후속 exact resolver가 실행될 기회 자체가 사라지는 누락이 핵심 위험이다.
- `constraints`: 가장 큰 병목이다. 33개 중 8개를 놓치고 7개를 잘못 만들었다. 투자지역·투자자산처럼 복합 대상 표현 안에 포함된 조건의 분리가 약했다.
- `relations`: 관계 필요 여부를 1건 놓치고 1건 오탐했다. 관계가 있다고 판단한 뒤 실제 경로의 의미가 맞는지는 영역 3의 `relation 양끝`이 별도로 평가한다.
- `ordering`: 생성된 6개 정렬 필드는 모두 맞았지만 필요한 정렬 1개를 누락했다. 정렬 방향까지 맞았는지는 별도 Exact 83.3%다.
- `computation`: 비교·중복도 같은 계산 요구 10개 중 5개만 회수했다. q016·q020·q028·q029처럼 “비교해줘”가 있어도 `compare`를 만들지 않은 사례가 반복됐다.
- `ambiguity`: 본 35문항에 있는 모호 유형 2개는 모두 찾았지만 정상 표현 2개를 추가로 모호하다고 판단했다. 별도 12문항 안전성 평가는 5.5절에서 다룬다.
- `validation_targets`: 검증 필요 여부뿐 아니라 유형까지 맞춘 TP는 3/5다. 존재 검출 4/5와 구분해서 읽어야 한다.

### 5.4 영역 4a — Validation 안전성

validation은 세 지표를 구분한다.


| 지표             | 계산                                            | 결과   | 기준   | 판정   | 의미                                       |
| -------------- | --------------------------------------------- | ----: | ----: | ---- | ---------------------------------------- |
| 존재 Recall      | 검증 대상 5문항 중 `validation_targets`가 하나라도 생성된 문항 | 4/5  | 5/5  | FAIL | q033을 제외한 4문항에서 위험 신호 자체는 감지했다.          |
| 유형 Recall      | gold validation 유형과 예측 유형이 일치한 항목             | 3/5  | 5/5  | FAIL | q032를 `future_value`로 오분류했고 q033은 미검출했다. |
| False Positive | 정상 30문항 중 validation을 생성한 문항                  | 1/30 | 0/30 | FAIL | q026을 `relation_domain_range`로 잘못 의심했다.  |


존재 Recall 4/5와 유형 Recall 3/5가 다른 이유는 **위험하다고 표시하는 것**과 **왜 위험한지 올바르게 분류하는 것**이 별도 능력이기 때문이다. 유형이 틀리면 후속 validator가 잘못 선택될 수 있다.

감사 로직은 프레임 분해와 별도 LLM 호출로 실행했다. 한 프롬프트에서 두 작업을 함께 수행했을 때 validation Recall은 1/5였고, 분리 후 존재 Recall이 4/5까지 개선됐다. `validation_targets` 배열을 직접 채우게 했을 때는 “무언가를 써야 한다”는 출력 압력으로 정상 30문항 모두에 오탐이 발생했다. `normal`을 첫 enum 값으로 둔 단일 verdict 방식으로 바꾸자 오탐이 30/30에서 1/30으로 감소했다.

미검출은 a06의 `요즘 잘 나가는` 1건이다. 그러나 12문항 모두에서 모호 표현을 임의의 수치·등급·기간으로 바꾸지 않았다. 즉, **질문을 되묻거나 후속 grounding이 필요한 표현을 놓친 사례는 1건 있지만, 근거 없는 확정으로 오답 필터를 만든 사례는 없었다.**

### 5.7 영역 5 — Downstream TBox 검색 A/B

#### 평가 설정

- 인덱스: `common.ttl`, `bond_kr.ttl`, `etf_kr.ttl`, `etf_gl.ttl`, `fund_pub.ttl`의 comment 보유 resource 188개
- 임베딩 문서 단위: resource 1개당 `uri | label | altLabel | comment` 1개
- 검색 방식: cosine similarity 상위 K
- gold: 문항별 `grounded_concepts`
- 분모: gold concept 중 `schema_terms_all`에 실제 존재하는 concept만 사용
- K: 1, 3, 5, 10, 20; 실제 운영 지점은 `config.BOND_TOP_K=5`

`R@K = 상위 K 결과에 포함된 gold concept 수 / 검색 가능한 전체 gold concept 수`다. 이는 “문항 중 하나라도 맞힌 비율”이 아니라 모든 문항의 검색 가능한 gold concept을 합산한 micro recall이다



#### 비교군


| Arm       | 검색 입력                                                             | 목적                            |
| --------- | ----------------------------------------------------------------- | ----------------------------- |
| A 질문원문    | 사용자 질문 전체를 한 번 검색                                                 | 기존 기준선                        |
| B 슬롯연결    | targets·constraint field·relation path·requested field를 한 문자열로 연결 | 프레임이 원문을 대체할 수 있는지 확인         |
| B′ 슬롯개별병합 | 각 슬롯을 따로 검색한 뒤 URI별 최고 유사도로 병합                                    | 여러 개념이 한 벡터에서 평균화되는 문제를 회피    |
| A+B′ 혼합   | 원문 검색과 슬롯별 검색 결과를 URI별 최고점으로 병합                                   | 원문 문맥을 보존하면서 슬롯의 추가 recall 확보 |


#### 결과


| Arm         | R@1      | R@3       | R@5       | R@10  | R@20  |
| ----------- | --------: | ---------: | ---------: | -----: | -----: |
| A 질문원문      | 3.3%     | 9.0%      | 13.1%     | 23.2% | 35.5% |
| B 슬롯연결      | 1.1%     | 6.3%      | 11.7%     | 22.1% | 40.7% |
| B′ 슬롯개별병합   | 4.1%     | 8.2%      | 12.0%     | 17.8% | 33.3% |
| **A+B′ 혼합** | **4.4%** | **10.1%** | **15.8%** | 22.7% | 37.4% |


운영 지점 `K=5`에서의 차이는 다음과 같다.


| Arm  | R@5   | A 대비 절대 변화 | A 대비 상대 변화 |
| ---- | -----: | ----------: | ----------: |
| B    | 11.7% | -1.4%p     | -11%       |
| B′   | 12.0% | -1.1%p     | -8%        |
| A+B′ | 15.8% | +2.7%p     | +21%       |


**부정 결과:** Query Frame은 질문 원문을 대체하지 못한다. B는 여러 의미를 한 문자열과 한 벡터로 평균내면서 R@1~R@10이 모두 기준선보다 낮아졌다. B′도 짧은 슬롯 표현의 개별 유사도만으로는 원문 문맥을 잃어 R@3 이상에서 기준선을 밑돌았다.

**활용 가능한 결과:** 원문을 유지한 `A+B′`는 K=1·3·5에서 개선됐고, 운영 지점 K=5에서는 13.1%에서 15.8%로 상승했다. 따라서 권고안은 **원문을 프레임으로 교체하는 것**이 아니라 **원문 검색 결과에 슬롯별 검색 결과를 보강하는 것**이다.

단, `A+B′`도 K=10에서 22.7%로 A의 23.2%보다 낮으므로 “모든 K에서 기준선 이상”이라는 사전 통과 기준은 만족하지 못한다. K=5 개선은 운영 지점에 한정한 결론이다.

```bash
python3 eval_query_frame.py --ambiguous
python3 build_tbox_index.py
python3 eval_query_frame.py --downstream
```

- `--check-gold`: LLM·네트워크 없이 35문항 ID, enum, 원문 span, limit 교차 일관성을 검사한다.
- `--audit`: 기본 프레임 추출 뒤 별도 감사 호출로 `validation_targets`를 대체한다.
- `--ambiguous`: 별도 12문항에서 모호 span과 premature resolution을 검사한다.
- `build_tbox_index.py`: 운영 인덱스를 건드리지 않고 평가 전용 188용어 테이블을 만든다.
- `--downstream`: 저장된 프레임으로 A/B/B′/A+B′ 검색을 비교한다.

현재 `eval_query_frame.py`의 gold 참조 상수는 과거 경로인 `vectordb_test/action3_semantic_schema/gold`를 가리키지만 실제 파일은 `vectordb_test/4_semantic_schema_nl2sql/gold`에 있다. 따라서 현 작업트리에서 위 명령을 그대로 재실행하면 `FileNotFoundError`가 발생한다. **기존 결과 파일을 재현하기 전에 이 경로를 현재 디렉터리 구조에 맞게 수정해야 하며**, 이 README 재작성에서는 평가 코드와 기존 결과 파일을 변경하지 않았다.

또한 35회 LLM 호출은 API 상태에 따라 지연과 출력이 달라질 수 있다. guard 변경 효과만 비교할 때는 새 LLM 호출 대신 저장된 `_raw`에 `--rescore`를 적용해야 모델 출력 변동과 후처리 효과를 분리할 수 있다.

## 9. 최종 권고

1. **Query Frame v1을 전체 신뢰 계약으로 승격**하지 않는다.
2. `operator`, `unit`, `temporal.kind`는 guard 이후 값만 사용한다.
3. constraints·computation·relation·role·validation 유형은 Planner 힌트로만 전달하고 metadata/TBox/원문으로 재검증한다.
4. **TBox 검색은 질문 원문 A를 유지하고, 운영 K=5에서만 확인된** `A+B′` **슬롯별 병합을 보조 recall 경로로 사용**한다.
5. 다음 수정은 복합 target/constraint 분리, 비교 trigger, 한국어 큰 수 파서, 자연어 relation path 제한의 네 일반 규칙에 한정해 재평가한다.
6. 수정 전후 비교는 동일한 저장 `_raw` 재채점과 신규 holdout 질의를 함께 사용해 guard 효과와 일반화 성능을 분리한다.

최종 상태는 “부분 채택: 핵심 의미 슬롯은 사용 가능, 실행 계획 전체를 맡기기에는 미달”이다.
