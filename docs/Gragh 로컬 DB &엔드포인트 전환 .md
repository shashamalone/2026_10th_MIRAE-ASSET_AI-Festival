## Gragh 로컬 DB > 엔드포인트 전환 작업

- tools/graph.py의 sparql() 한 함수만 교체
- 상위 전부(graph_entity·graph_plan·text2sparql)가 이 함수 하나만 호출하도록 이미 정리

┌──────┬──────────────────────────────┬─────────────────────────────────────────────────────┐
│ 항목 │             로컬             │                         API                         │
├──────┼──────────────────────────────┼─────────────────────────────────────────────────────┤
│ 실행 │ Store.read_only(...).query() │ POST /db/sparql {"sparql": ...}                     │
├──────┼──────────────────────────────┼─────────────────────────────────────────────────────┤
│ 반환 │ [{var: value}]               │ {"columns":[], "rows":[], "row_count", "truncated"} │
├──────┼──────────────────────────────┼─────────────────────────────────────────────────────┤
│ ASK  │ bool                         │ 응답 형태 미확인 (전환 전 확인 필요)                │
└──────┴──────────────────────────────┴─────────────────────────────────────────────────────┘

rows가 이미 dict 리스트라 형태 변환은 거의 없고, 필요한 건 ① requests.post 래핑 ② truncated 플래그를 MAX_ROWS 초과와 동일하게 취급 ③ manifest.json cutoff 검증을 /health의 release_id 검증으로 교체 ④ 로컬/API 전환 스위치(config.GRAPH_BACKEND) 정도

단 성능은 반드시 재측정해야 합니다. 
- 지금 X1 fast path가 0.03초인데, 원격 호출은 왕복 지연이 붙습니다. 
- graph_entity가 엔티티 해소 때 ASK를 여러 번 날리는 구조라 15초 예산에 직접 영향이 갑니다.
