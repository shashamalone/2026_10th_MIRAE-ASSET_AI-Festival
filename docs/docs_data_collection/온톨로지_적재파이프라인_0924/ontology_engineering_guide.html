1. TBox 개요

1.1 구축 목적 및 범위

TBox는 금융상품 질의에서 상품 유형·관계 방향·허용된 분류·근거 요건을 고정하는 의미 모델이다. 숫자 계산은 RDB가 수행하고, 그래프는 다중 홉 관계와 domain/range 제약을 담당한다.

구현 구분: TBox는 현재 build_graph.py가 생성하지 않는다. 사람이 설계한 ontology/*.ttl이 TBox이고, build_ontology_instances.py가 ABox를 생성하며, build_graph.py가 TBox+ABox를 Oxigraph에 적재한다.

범위는 국내채권, 국내 ETF, 해외 ETF, 국내 공모펀드와 이들 사이의 기관·증권·테마·편입·자회사·근거문서 관계다. 룩어헤드 값, 전량 dummy 값, 확인되지 않은 분류는 그래프에서 제외하거나 미매핑으로 남긴다.

2. Class 설계

2.1 Class Hierarchy

Product├─Bond├─ETF├─ETN└─PublicFund
Organization→Company/Issuer/AssetManager/Custodian

Bond와 ETF는 상품인 동시에 편입 가능한 Security이고, PublicFund는 Product의 하위다. ShareClass는 PublicFund의 하위로서 개별 종목번호를 가진 판매 단위를 표현한다.

2.2 Class 정의

기관Organization, Company, Issuer, AssetManager, Custodian기업·채권 발행기관·운용사·수탁사를 역할별로 구분한다.

2.3 Instance 생성 기준

  • 국내채권: 원천 복합키를 보존하되 상품 URI는 pd_no 기반으로 생성한다.
  • 국내 ETF: pd_grp_no='ETF'만 적재하고 오염키 KR은 제외한다.
  • 해외 ETF/ETN: pd_grp_no로 유형을 나누어 동일 원천에서 생성한다.
  • 펀드: itm_no가 단독 상품키다. 공모는 PublicFund, 사모·구분 결측은 Product로 선언한다.
  • 기업: 모든 기업을 무조건 그래프로 만들지 않고 편입·발행·자회사 관계에서 참조되는 기업을 생성한다.

3.2 관계 방향

관계는 질의가 시작되는 주체에서 의미상 대상 방향으로 정의한다. 예를 들어 ETF → hasHolding → Holding → holdingSecurity → Security → issuedByCompany → Company는 “ETF가 어떤 기업의 증권을 편입했는가”를 표현한다.

3.3 역관계

sameVehicleAs는 owl:SymmetricProperty로 선언했다. 다만 현재 Oxigraph 런타임은 자동 추론에 의존하지 않으므로 양방향 탐색이 필요한 경우 양쪽 triple을 직접 생성하거나 질의에서 양방향을 명시해야 한다. subsidiaryOf는 전이성으로 선언하지 않는다. 지분율과 투자목적이 관계마다 달라 손자회사 탐색은 SPARQL 경로 탐색으로 수행한다.

3.4 관계 사용 조건

관계가 존재한다는 것과 답변 가능한 근거가 있다는 것은 다르다. supportedBy·asOf·원천 source를 확인하고, 기준일을 모르면 날짜를 추정하지 않는다.

4. Datatype Property 설계

4.1 Domain

Datatype property는 가능한 주체를 좁게 선언한다. 예를 들어 maturityDate는 Bond, ticker는 ETF/ETN, saleStatus는 PublicFund에 귀속한다. 여러 도메인에 공통인 속성은 OWL anonymous union으로 명시한다.

4.2 Datatype

종류예시표현
문자열productName, ticker, organizationNamexsd:string
날짜issueDate, maturityDate, asOfxsd:date
수치weight, couponRate, ownershipPctxsd:decimal
논리값isInverse, isSellable, currencyHedgedxsd:boolean
순서값ratingRankxsd:integer

4.3 값 형식 및 제약

  • 모든 owl:DatatypeProperty에는 fp:sourceTable과 fp:sourceColumn을 기록한다.
  • 파생값은 derived:파일명.컬럼명으로 원본값과 구분한다.
  • 결측·sentinel은 실제 의미에 따라 triple을 생략하거나 상태값으로 변환한다. 예: 국채 등급 결측은 UnratedByDesign.
  • 전량 dummy인 괴리율·추적오차 등은 property 자체를 온톨로지에 올리지 않는다.
  • weight·ownershipPct 결측은 임의의 0으로 치환하지 않고 triple을 생략한다.

5. Graph Relation Pattern ★

5.1 기업-자회사

?parent a fp:Company ; fp:hasSubsidiary ?rel .
?rel a fp:SubsidiaryRelation ; fp:subsidiaryCompany ?child ;
     fp:ownershipPct ?pct ; fp:asOf ?date ; fp:supportedBy ?doc .

실제 관계는 DART 원천 및 접수일을 이용해 생성하며, 기준일 초과 관계는 적재 대상에서 제외한다. 단순히 “출자”가 있다고 해서 모두 지배 자회사라고 해석하지 않는다.

5.2 ETF-Holding-Security

?etf a fp:ETF ; fp:hasHolding ?holding .
?holding a fp:Holding ; fp:holdingSecurity ?security ;
         fp:weight ?weight ; fp:asOf ?asOf ; fp:supportedBy ?doc .

편입비중·기준일·문서를 Holding 노드에 함께 둔다. ETN에는 hasHolding을 연결하지 않는다.

5.3 상품-발행사

채권은 Bond → issuedBy → Issuer이고, 편입증권은 Security → issuedByCompany → Company다. ETF의 운용사를 발행사 관계로 잘못 연결하지 않도록 두 관계를 분리한다.

5.4 상품-테마

Product → relatedToTheme → Theme를 사용한다. 현재 테마는 국내 ETF 1,099종·176종 테마·5,646 관계가 중심이며 etf_theme.as_of가 공란이므로 기간 질의에 날짜 근거로 사용하지 않는다.

5.5 관계-근거문서

Holding·SubsidiaryRelation 등 사실 노드는 하나의 Document에 연결하며 문서명·발행기관·발행일·인용문을 필수로 검증한다. 근거문서에 함께 언급되었다는 사실만으로 관계를 새로 추론하지 않는다.

6. Semantic Definition ★

6.1 Class 의미

Class는 원천 컬럼명이 아니라 질의에서 구분되어야 하는 금융상품·기관·관계·분류 개념이다. 예컨대 ETN은 ETF 원천 파일에 함께 들어 있어도 편입종목 개념이 없으므로 별도 Class로 분리한다.

6.2 Property 의미

Property의 comment에는 적용 대상, 원천 컬럼, 결측·sentinel 처리, 답변 가능성에 영향을 주는 규칙을 기록한다. 이 comment와 label은 schema grounding 및 자연어 term retrieval의 입력이다.

6.3 포함/제외 기준

포함

질의 필터·조인·관계 탐색에 직접 필요한 식별자, 분류, 수치, 기준일, 근거 속성.

제외

전량 dummy, 의미 미확정 코드, 룩어헤드 값, 근거 없는 추정 매핑, RDB가 더 정확히 처리하는 파생 플래그.

미매핑은 조용히 폐기하지 않고 builder가 값·건수를 출력한다. 현재 결정 대기 대표 사례는 레버리지 ±0.5/±1.5, 채권 만기 미상, 지방채 분류, 해외 ETF 국가→지역 매핑이다.

8.2 Canonical ID

RDB 원천키를 canonical ID로 사용한다. 채권 물리 PK는 (pd_no,pd_exg_mkt,info_seq) 전체를 보존하며, 펀드는 itm_no 단독키다. 기업은 DART corp_code가 최우선 식별자다.

8.3 Entity 동일성 기준

  • 동일 상품 추정은 이름 유사도가 아니라 검증된 식별자 교집합으로 판정한다.
  • 펀드 KSD code와 국내 ETF pd_itm_no가 일치하는 47종은 sameVehicleAs로 연결하되 서로 다른 URI를 유지한다.
  • 기업명은 법인격·한글 음차를 정규화하고 DART code가 있으면 code 기반 노드를 사용한다.
  • 동일 코드가 없는 증권은 원천 코드·종목명·코드 유형을 함께 보존하며 불확실한 병합을 피한다.

9.3 FK/ID → URI

상품 foreign key는 정규화된 상품 URI로, holding code는 Security URI로, DART corp_code는 Company URI로 변환한다. 채권은 복합키로 RDB join을 수행하고, URI 생성 시 상품 식별자와 관계의 sequence를 분리한다.

9.4 변환·정규화 규칙

  • URI에 사용할 수 없는 문자는 UTF-8 percent encoding, 한글은 가독성을 위해 유지한다.
  • 기업명에서 (주), ㈜, 공백 등을 제거하고 에스케이→SK, 엘지→LG 등의 alias를 적용한다.
  • 원천 sentinel은 명시적으로 NULL·상태·적재 제외로 구분한다.
  • 주최측 명칭과 외부 명칭이 충돌하면 주최측을 표시명으로 유지하고 충돌을 evidence에 남긴다.
  • builder는 입력 순서를 정렬해 결정적 TTL을 생성하며 매핑 실패 건수를 출력한다.

10. Ontology Validation

10.1 Domain/Range

validate_ontology.py가 모든 Object/Datatype property의 domain·range 존재 여부와 ABox의 실제 주어·목적어 타입을 검사한다. subclass closure와 unionOf를 확장해 검사하며, ETF에 Bond 전용 issuedBy를 붙이는 오류를 차단한다.

10.2 Cardinality

현재 TBox에 전면적인 OWL cardinality restriction이나 SHACL shape를 두지는 않았다. 대신 관계별 계약을 validator에 구현한다. 예: cutoff 내 Holding/SubsidiaryRelation은 정확히 하나의 supportedBy 문서를 가져야 한다.

10.3 필수 속성

  • 모든 TBox entity: rdfs:label
  • 모든 typed property: rdfs:domain, rdfs:range
  • 모든 datatype property: fp:sourceTable, fp:sourceColumn
  • 관계 evidence 문서: type, title, publisher, published date, quote
  • 관계 노드: 관계별 asOf·source·supportedBy 계약

10.4 관계 방향

validator는 Holding, SubsidiaryRelation의 필수 경로와 대표 spot check를 검증한다. 대표 경로는 Company → SubsidiaryRelation → Company → Security → Holding → ETF다.

10.5 SHACL/Validator 규칙

현재 구현: SHACL(pySHACL)이 아니라 Python 검사와 Oxigraph SPARQL ASK/SELECT를 사용한다. 설계 기록에서도 검증 항목이 domain/range·등급·출처·cutoff 중심이어서 SPARQL validator를 선택했다.

11. 대표 Mapping 사례

11.1 원천 데이터

예시 질문은 “에코프로의 자회사가 편입된 ETF는?”이다. 입력에는 company_master.csv, company_subsidiary.csv, holding_code_map.csv, etf_holding.csv와 DART·운용사 원천 evidence가 사용된다.

11.2 Entity Resolution

기업명 에스케이하이닉스(주)와 SK하이닉스는 법인격·음차 정규화 후 비교한다. 가능하면 DART corp_code를 canonical ID로 채택하고, 불확실하면 임의 병합하지 않는다.

11.3 Triple 생성

fpi:corp-01234567 a fp:Company ; rdfs:label "에코프로" .
fpi:sub-01234567-에코프로비엠-0 a fp:SubsidiaryRelation ;
    fp:subsidiaryCompany fpi:corp-01160363 ;
    fp:ownershipPct "..."^^xsd:decimal ;
    fp:asOf "2026-07-11"^^xsd:date ;
    fp:supportedBy fpi:doc-... .
fpi:sec-247540 a fp:Security ;
    fp:issuedByCompany fpi:corp-01160363 .
fpi:hold-KODEX-247540-0 a fp:Holding ;
    fp:holdingSecurity fpi:sec-247540 ;
    fp:weight "..."^^xsd:decimal ;
    fp:asOf "2026-07-10"^^xsd:date ;
    fp:supportedBy fpi:doc-... .
fpi:etfkr-KR... a fp:ETF ; fp:hasHolding fpi:hold-KODEX-247540-0 .

11.4 최종 Graph 구조

에코프로→ hasSubsidiary →에코프로비엠← issuedByCompany ←247540 Security← holdingSecurity ←Holding← hasHolding ←ETF

최종 응답에는 ETF 목록뿐 아니라 각 편입관계의 비중·기준일·source, 자회사 관계의 기준일·DART 문서, 그리고 “확인 불가”인 경우 그 사유를 함께 전달한다.

현재 한계: Graph Store와 SPARQL runtime은 코드상 빌더·읽기 전용 인터페이스가 준비되어 있으나 환경에 따라 pyoxigraph가 설치되어 있어야 한다. 해외 ETF·공모펀드 편입관계, 일부 해외 종목 Entity Resolution, 테마 기준일 미상은 여전히 데이터 갭으로 표시해야 한다.
