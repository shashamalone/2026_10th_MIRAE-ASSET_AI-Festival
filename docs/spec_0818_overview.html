01질의 처리 파이프라인

핵심은 LLM이 연산하지 않는다는 것이다. LLM은 질의를 분류하고(①), 실행 계획을 쓰고(③), 결과를 문장으로 포장한다(⑤). 실제 필터·조인·정렬은 전부 파이썬 코드와 세 엔진이 한다.

023계층 스택과 경계

2단계가 만드는 것은 엔진 3개와, 3·4단계가 호출할 함수 4개다. 라우팅·분해·통합은 넘기지 않는다 — 그건 3단계 소관이다.

계층엔진선정 근거
RDBDuckDB집계·조인에서 SQLite 대비 10~100배. CSV 직접 질의로 적재가 짧다
Graphpyoxigraph기존 .ttl을 변환 없이 벌크 로드. rdflib은 100만 트리플에서 수십 초 — 예산을 소진한다
VectorFAISSCLOVA bge-m3 1024차원 cosine. 1만 청크 미만이라 인덱스 구조가 자유롭다
LLMChatClovaXHyperCLOVA X 전용 제약. 분류는 HCX-DASH-002, 계획·생성은 HCX-007
동시 사용 불가

CLOVA Studio는 function calling · structured outputs · thinking을 동시에 못 쓴다. 3단계는 structured outputs를 쓰므로 라우팅을 LLM tool call로 하지 않는다 — 반환된 JSON 계획을 파이썬 코드가 해석·실행한다.

03TBox가 엔진이다

“안전한”은 어떤 컬럼에도 없다. 이 말을 데이터가 아는 조건으로 번역하는 것이 rdfs:comment다. 기술세션 벤치마크가 프롬프트 주입 +2.4pp / 런타임 식별 +20pp로 갈린 이유가 여기 있다.

이 저장소의 TTL은 이미 그렇게 쓰여 있다. 주석이 사람용 설명이 아니라 실행 지시서다.

fp:ratingRank  rdfs:comment
  "1=AAA(최상) … 19=C(최하). 'AA- 이상'은 fp:ratingRank <= 4로 판정한다.
   data/enriched/bond_kr_enriched.csv의 crd_grd_rank와 동일 체계이므로
   RDB 선필터와 온톨로지 판정 결과가 일치한다."@ko

fp:riskGradeLevel  rdfs:comment
  "1=최고위험 … 6=최저위험. 채권·국내ETF·공모펀드 세 도메인의 서열 방향이 모두 같다."@ko

실측한 주석 보유 현황이다. 이 193개가 그대로 스키마 인덱스의 청크가 된다.

1차 기획의 2단계는 “모든 속성의 rdfs:comment를 임베딩해 둔다”를 전제한다. 성립한다. 남은 일은 클래스·속성 총계 약 240개 대비 부족한 약 47개를 채우는 것뿐이고, 이건 2단계 인덱스 구축 전에 선행한다.

04Vector 인덱스 분리

1차 기획을 반영하며 바꾼 유일한 구조다. 스키마 검색과 근거 검색은 규모도, 갱신 주기도, 메타데이터도 다르다 — 한 인덱스에 두면 서로를 오염시킨다.

실행 불가 구간

cu_strtegy는 해외ETF에만 있다. 1차 기획의 예시(“안전한 ETF”)는 국내ETF 질의이므로 근거 텍스트가 현재 존재하지 않는다. 투자설명서 확보 전까지 국내ETF 답변의 “왜 안전한가”는 위험등급·레버리지 분류 근거로 한정하고, 없는 근거를 지어내지 않는다.
