## 온톨로지 구축 프로세스_v.2.1_260822

예시 질문 : "안전한 ETF 추천해줘"

- 가장 까다로운 유형
- "안전한"이 어떤 컬럼에도 없음



### 1단계 :  Query Understanding - LLM기반 의미 분해(대상/조건/행위)

첫 단계는 Query Understanding - LLM이 자연어를 의미 단위로 분해

- "안전한 ETF 추천해줘"에서 뽑아야 할 것은 세 가지입니다. **대상은 ETF, 조건은 "안전한"(모호), 행위는 추천(상위 N개 정렬)**
- 여기서 핵심 문제는 "안전한"이 데이터에 직접 매핑되지 않음

**[1단계] Intent Classification — 가볍게, TBox 없이**

- 가볍게, TBox 없이
- 입력: 사용자 질의 원문
- 출력: {도메인, 질의유형, 핵심 키워드}
- 방법: 소형 분류기 또는 LLM 1회 호출 (system prompt 짧음)

```json
# 1단계 결과 (LLM 또는 분류기)
{
  "domain": ["etf_kr"],           # "ETF" → 국내ETF
  "query_type": "recommendation", # "추천해줘" → 추천형
  "keywords": ["안전한"],          # 모호한 조건 원문 보존
  "numeric_filters": [],          # 구체적 숫자 조건 없음
  "entities": []                  # 특정 상품명 없음
}
```

- 주의
  - 1단계에서 도메인 판별이 틀리면 2단계에서 엉뚱한 속성을 검색
    - ”미국 채권형 ETF"라고 하면 채권인지 해외ETF인지 헷갈림
    - 이때 1단계에서 다중 도메인을 허용하고(`["etf_gl", "bond_kr"]`), 2단계에서 두 도메인의 메타데이터를 함께 검색해서 3단계 LLM이 최종 판단하게 할 것

### 2단계 :  Ontology Grounding -  Schema Retrival 기반 Tbox Comment에서 모호한 의미 → 측정가능한 의미로 번역

두 번째 단계가 Ontology Grounding, TBox를 참조해서 "안전한"을 데이터가 아는 속성으로 번역

예) TBox에 다음이 선언되어 있다고 파악

```json
fp:riskGrade  a owl:DatatypeProperty ;
    rdfs:comment "1=최고위험, 6=최저위험. 숫자가 클수록 안전"@ko .
fp:totalExpenseRatio  a owl:DatatypeProperty ;
    rdfs:comment "연 총보수(%). 낮을수록 비용 부담 적음"@ko .
fp:leverageFactor  a owl:DatatypeProperty ;
    rdfs:comment "1=일반, 2이상=레버리지, 음수=인버스"@ko .
    

[참고] rdfs:comment는 사람을 위한 주석이 아니라 LLM을 위한 지시서
# rdfs:comment가 없을 때 — LLM이 보는 정보
fp:riskGrade a owl:DatatypeProperty .
# → LLM: "riskGrade... 1이 낮은 위험인가? 높은 위험인가?"

# rdfs:comment가 있을 때 — LLM이 보는 정보  
fp:riskGrade a owl:DatatypeProperty ;
    rdfs:comment "1=최고위험(매우높은위험), 6=최저위험(매우낮은위험). 숫자가 클수록 안전"@ko .
# → LLM: "안전한 = 숫자가 큰 것 = 5~6 → WHERE pd_risk_cd >= 5"
```

- LLM은 `rdfs:comment`라는 메타데이터를 읽고 "안전한 = 위험등급 높은 숫자(5~6등급) + 레버리지 1배 + 인버스 아님"으로 분해
- 이게 온톨로지가 "설명이 아니라 실행에 쓰일 때 +20pp"인 이유
- **rdfs:comment가 없으면 LLM이 `pd_risk_cd`를 보고 "1이 안전한 건가 위험한 건가"를 추측**해야 함

**[2단계] Schema Retrieval — TBox에서 필요한 부분만 검색**

- 입력: 1단계 결과 (도메인 = "국내ETF", 키워드 = "안전한")
  - "안전한"이라는 키워드로 TBox 메타데이터 벡터 인덱스를 검색합니다. TBox의 모든 속성의 rdfs:comment를 미리 임베딩해서 벡터 DB에 넣어둔 상태
- 출력: 관련 속성 메타데이터 3~5개
- 방법: TBox 메타데이터를 벡터 인덱스에 넣어두고 유사도 검색
- **유지 보수**
  - TBox TTL 파일에서 rdfs:comment를 수정하면, 벡터 인덱스를 재구축하는 스크립트를 한 번 돌리면 끝입니다. system prompt를 고칠 필요가 없습니다. 속성이 추가돼도, 삭제돼도 동일합니다. 인덱스만 갱신하면 됩니다.

### 3단계 :  Plan &amp; Routing - LLM기반의 DB 탐색 계획(GraghDB, RDB, VectorDB 순차 탐색 or 병렬 탐색)

세 번째 단계가 Plan &amp; Routing입니다. 분해된 조건을 어디로 보낼지 정하기

```
"안전한 ETF 추천해줘"
    │
    ├─ [Graph] 위험등급 5~6등급인 ETF (코드 분류 → ABox)
    ├─ [Graph] 레버리지 1배, 인버스 아님 (코드 분류 → ABox)
    ├─ [RDB]  순자산 상위 정렬 (숫자 → SQL)
    ├─ [RDB]  총보수 낮은 순 정렬 (숫자 → SQL)
    └─ [Vector] "안전", "저위험", "안정적" 관련 투자전략 문서
              (cu_strtegy 텍스트 — 해외ETF에만 있음)
```

**[3단계] Query Planning — 검색된 메타데이터만 넣고 LLM 호출**

- 입력: 사용자 질의 + 2단계에서 검색된 속성 설명 3~5개
  - 3 단계에서 LLM에 들어가는 prompt는 전체 TBox가 아니라 2단계에서 검색된 속성 3~5개만 들어감
  - 이렇게 하면 LLM이 보는 context가 짧고 정확, 채권·펀드 메타데이터가 안 섞이니 혼란이 없고, "1=최고위험"이라는 방향이 명시돼 있으니 반대로 쓸 일이 없음
  
      **예시 시스템 프롬프트**
- 출력: 실행 계획 (SQL/SPARQL/Vector 조합)
  - 3단계의 출력물⇒ LLM이 만드는 건 "어디서 뭘 가져와라"라는 실행 계획서
  - 계획 자체는 1회 생성이고, 실행은 의존 관계에 따라 병렬과 순차가 섞일 수 있음
  - A(Graph)와 B(Vector)는 서로 의존이 없으니 동시에 보낼 수 있음.
  - C(RDB)는 A의 결과(후보 목록)가 있어야 `WHERE IN`에 넣을 수 있으니 A가 끝난 후에 실행됨
  - **⇒ 질의 유형에 따라 의존 관계가 달라지므로 어떻게 진행해야할 지 프롬프트에 명시 필요함**
  - **예시 실행 코드(병행 vs 직렬 병행)**
- 방법: LLM 1회 호출 (context에 필요한 메타만 들어감)

**[35개 예시 질의 유형 기반 전략 - 6개 유형]**


| 유형1 | RDB 단독             | 14건    | 40.0% | 병렬 해당 없음 |
| --- | ------------------ | ------ | ----- | -------- |
| 유형2 | Graph → RDB 순차     | 4건     | 11.4% | 병렬 불가    |
| 유형3 | Graph → RDB+Vector | 2건     | 5.7%  | 부분 병렬 가능 |
| 유형4 | Graph 다단계 → 순차전체   | 8건     | 22.9% | 병렬 거의 불가 |
| 유형5 | Graph 단독           | 2건     | 5.7%  | 병렬 해당 없음 |
| 유형6 | TBox 검증 단독         | 5건     | 14.3% | 병렬 해당 없음 |
|     |                    | 합계 35건 | 100%  |          |


1. 병렬이 의미 있는 문항은 유형 C의 2건뿐(5.7%)입니다. 나머지 33건은 단일 엔진이거나 순차 의존입니다. "병렬화로 시간을 아낀다"는 건 소수 문항에서만 효과가 있고, 대다수는 단일 엔진 속도 자체가 관건입니다.
2. 그런데 이건 현재 데이터 기준입니다. 근거 문서(투자설명서·운용보고서)가 확보되면 상황이 바뀝니다. 유형 A 14건 중 상당수가 "RDB 결과 + Vector 문서 근거"를 함께 내야 하므로 유형 C로 승격됩니다. 문서 확보 후 예상 분포는 이렇습니다.
3. 문서 확보 후에는 병렬 가능 비율이 5.7% → 34.3%로 올라갑니다. 이때 비로소 `asyncio.gather`로 RDB와 Vector를 동시에 돌리는 구조가 실질적 시간 절약 효과를 냅니다.
4. 실무적으로 가장 중요한 발견은 — 유형 D(다단계 순차) 8건이 전부 상 난이도이고, 전부 현재 불가 판정이라는 점입니다. 이 8건은 편입종목·자회사·문서 세 축이 전부 필요하고, 순차 의존이라 경로가 길어서 응답 예산에 가장 위험합니다. Graph 쿼리 최적화(경로 캐싱, 중간 결과 물질화)가 이 8건의 응답 시간을 결정합니다. *(→ 정정 C1: 예산은 60초 / 정정 C6: 8건 전부 불가가 아니라 불가는 23·25·30 3건이고 나머지 5건은 부분이다)*
5. 구현 우선순위를 정하면 — 유형 F(5건, TBox 검증)를 먼저 만드는 게 가장 효율적입니다. LLM 호출 없이 규칙 기반으로 판정하면 되고, 확실한 득점 구간입니다. 그 다음 유형 A(14건, RDB 단독)는 NL2SQL만 잘 되면 커버됩니다. 유형 D(8건)는 데이터 확보와 엔진 최적화가 모두 필요하니 마지막에 잡습니다.

- **유형 1 : RDB 단독. 숫자 필터·정렬·집계만으로 끝나는 질의**
  - Graph도 Vector도 필요 없고, 병렬 자체가 없음
  - 해당 문항: 1, 2, 3, 5, 6, 7, 8, 9, 10, 11, 12, 13, 17, 18 (14건)
  - 예시
    - "판매가능 원화채권 AA- 이상"(11번)은 `WHERE BUYABLE_QUANTITY > 0 AND CURR_CD = 'KRW' AND crd_grd_rank <= 4 ORDER BY BUY_YIELD DESC`로 끝남
- **유형 2 : Graph → RDB 순차. 분류 코드를 Graph에서 필터한 뒤, 그 결과 목록을 RDB에서 숫자 정렬**
  - 순차 의존이라 병렬이 안 됨
  - 해당 문항: 15, 16, 19, 20 (4건)
  - 예시
    - "액티브 ETF 중 AUM 5천억 이상, 테마별 6개월 수익률 비교"(16번)는 Graph에서 `replication=Active + theme`을 뽑고, RDB에서 AUM·수익률을 정렬
- **유형 3 :  Graph → RDB + Vector 병렬.**
  - Graph에서 후보를 뽑은 뒤, RDB 정렬과 Vector 근거 검색을 동시에 실행합니다. 이 과제에서 가장 이상적인 패턴
  - 해당 문항: 4, 26 (2건)
  - 예시
    - "우주항공 테마 ETF의 수익률과 투자전략"(4번)은 Graph에서 테마 필터 → RDB에서 수익률 정렬 + Vector에서 전략 텍스트 검색을 병렬로 돌림
- **유형 4 :  Graph 다단계 순차 → RDB → Vector 순차.**
  - 관계 경로를 여러 홉 따라간 뒤에 숫자 필터, 그 다음 문서 검색. 전부 앞 단계 결과에 의존하므로 병렬이 거의 불가능
  - 해당 문항: 22, 23, 24, 25, 27, 28, 29, 30 (8건)
  - 예시
    - "에코프로 자회사 편입 ETF 중 순자산 큰 것의 위험요인"(24번)은 에코프로 → 자회사(Graph 1홉) → 편입종목(Graph 2홉) → ETF 목록 → RDB 순자산 정렬 → Vector 위험요인 문서. 각 단계가 이전 결과를 먹으니 직렬
- **유형 5 : Graph 단독 (관계 확인만). 숫자 정렬이 없고, 관계 존재 여부만 확인하면 끝나는 질의**
  - 해당 문항: 14, 21 (2건)
  - 예시
    - "KODEX 200이 펀드와 동일 상품인지"(21번)는 `fund.ksd_itm_no == etf.pd_itm_no` 관계가 ABox에 있는지 확인만 하면 됩니다.
- **유형 6 : TBox 검증 단독 (답변불가 판정). 데이터를 검색하기 전에 TBox 어휘·도메인 선언으로 질문 자체의 성립 여부를 판단합니다. 엔진 호출이 필요 없거나 있어도 0건 확인만**
  - 해당 문항: 31, 32, 33, 34, 35 (5건)
  - 예시
    - "AAAA 등급 채권"(31번)은 TBox의 CreditRating 어휘에 AAAA가 없으므로 `ABSTAIN_INVALID_TAXONOMY`. "VOO의 발행사"(35번)는 TBox에서 `ISSUED_BY`의 domain이 Bond이므로 ETF에 적용 불가.

실제 실행을 순서대로 따라가면 이렇습니다.

단계 A — Graph에서 후보 필터링. SPARQL로 코드 조건을 걸어 후보 목록을 뽑습니다.

```
SELECT ?etf ?name WHERE {
  ?etf a fp:DomesticETF ;
       rdfs:label ?name ;
       fp:riskGrade ?rg ;
       fp:leverageFactor ?lev .
  FILTER (?rg IN (fp:Grade5, fp:Grade6))
  FILTER (?lev = "1")
  FILTER NOT EXISTS { ?etf fp:isInverse true }
}
```

결과: 위험등급 5~6등급이면서 레버리지 1배인 국내ETF, 예를 들어 115건.

단계 B — RDB에서 숫자 정렬. 위 115건의 `pd_itm_no` 목록을 SQL의 `WHERE IN`에 넣고 순자산·보수로 정렬합니다.

```sql
SELECT pd_itm_no, pd_abrv_nm, du_last_aum, ter
FROM etf_kr_enriched
WHERE pd_itm_no IN ('KR7...', 'KR7...', ...)  -- Graph 결과 115건
  AND du_last_aum > 0
ORDER BY du_last_aum DESC, ter ASC
LIMIT 10
```

결과: 순자산 크고 보수 낮은 상위 10개. "추천"의 실체가 여기서 만들어집니다.

단계 C — Vector에서 근거 텍스트 보강. 상위 10개의 투자전략 텍스트를 벡터 검색으로 가져옵니다. 해외ETF라면 `cu_strtegy`(평균 309자 서술)가 있고, 국내ETF라면 투자설명서 문서 청크가 대상입니다. "안전"이라는 질의 임베딩과 가장 가까운 문서 조각을 찾습니다.

```python
query_embedding = embed("안전한 저위험 안정적 투자")
results = vector_store.similarity_search(
    query_embedding,
    filter={"pd_itm_no": {"$in": top10_ids}},  # Graph+RDB 결과로 범위 한정
    top_k=5
)
```

이 단계가 없으면 "왜 이게 안전한지"를 설명할 근거가 없습니다. 위험등급 숫자만으로는 "채권형이라 주가 변동 위험이 낮고, 실물 복제 방식이라 파생상품 위험이 없다"는 서술을 만들 수 없습니다.

1. 단계 D — 통합 및 검증. 세 결과를 합칩니다.

```python
evidence = {
    "graph": {  # 어떤 분류 조건으로 걸렀는지
        "filters": ["위험등급 5~6등급", "레버리지 1배", "인버스 제외"],
        "source": "ontology/etf_kr.ttl, ABox"
    },
    "rdb": {  # 숫자 근거
        "columns": ["du_last_aum", "ter"],
        "sort": "순자산 내림차순, 보수 오름차순",
        "as_of": "2026-06-15"
    },
    "vector": {  # 텍스트 근거
        "chunks": ["채권형 ETF로 만기 1~2년 국채 중심 편입..."],
        "source": "투자설명서"
    }
}
```

1. 단계 E — LLM이 답변 생성. evidence를 받아서 사람이 읽을 답변을 만듭니다.

```
추천 결과: KODEX 단기채권, TIGER 단기통안채, KBSTAR 중기우량회사채...

근거:
- 위험등급: 5등급(낮은 위험) 또는 6등급(매우 낮은 위험)
- 레버리지: 1배(일반), 인버스 아님
- 순자산: 상위 10개 기준 (국내ETF 마스터, 2026-06-15 기준)
- 총보수: 0.05%~0.15% (출처: LSEG Lipper ter)
```

1. 여기서 Vector DB가 없었다면 어떻게 달라지냐
  1. 위험등급 5~6등급이라는 숫자는 나오지만, "왜 안전한가"에 대한 설명이 "위험등급이 낮아서"로 끝납니다. 투자설명서에 "국고채 및 통안채 위주로 편입하여 신용위험을 최소화"라는 문장이 있으면 답변의 질이 완전히 달라집니다. 또한 사용자가 "안전한"이라고 했을 때 "변동성이 낮은"을 의미하는지 "원금 손실 가능성이 낮은"을 의미하는지 벡터 유사도로 구분할 수 있습니다.
2. 반대로 Graph가 없었다면 — "위험등급 5등급 이상"을 SQL로 해도 되지 않냐는 의문이 생깁니다. 이 질의만 보면 맞습니다. 그런데 "안전한 ETF인데 반도체 테마인 것"이라고 조건이 붙는 순간 SQL로는 테마를 찾을 수 없습니다. 테마는 RDB 컬럼에 없고 Graph에만 있습니다. 또한 "안전한 ETF"라는 조건에서 위험등급뿐 아니라 "인버스 아님"을 걸어야 한다는 판단 자체가 TBox의 속성 설명(`rdfs:comment`)에서 나옵니다.
3. 전체 흐름을 시간축으로 보면 이렇습니다.

```
[0ms]     사용자: "안전한 ETF 추천해줘"
[0~500ms] LLM: 의도 분해 + TBox 참조 → 조건 3개 도출
[500~800ms] SPARQL: 코드 필터 → 후보 115건
[800~1200ms] SQL: 숫자 정렬 → 상위 10건
[1200~2000ms] Vector: 근거 텍스트 5건 검색
[2000~2500ms] 통합 + 검증 (SHACL: 등급값 유효? 출처 있음?)
[2500~4000ms] LLM: 답변 생성
[~4초]    총 응답 — 15초 제한 안에 여유
```

> ⚠️ 위 "15초"는 OT 구두 기준이다. **공식 값은 문항당 60초 이내 권장**(과제설명 PDF p11). 아래 「1차 기획 정정 사항」 C1 참조.

1. 마지막으로 Vector DB에 뭘 넣어야 하냐 — 이 프로젝트 기준으로 임베딩 대상은 세 가지입니다. 첫째, 해외ETF `cu_strtegy` 텍스트 5,566건(평균 309자, 가장 풍부). 둘째, 향후 수집할 투자설명서·운용보고서 문서 청크. 셋째, TBox의 클래스·속성 설명(rdfs:comment) 자체 — 이건 양이 적지만 "안전한 → 위험등급" 같은 자연어-속성 매핑에 결정적입니다. 각 임베딩에는 `pd_itm_no`(상품 식별자)와 `source`(출처)를 메타데이터로 붙여서 Graph·RDB 결과와 조인할 수 있게 합니다.

## 1. 1차 기획의 전제 검증 — TBox는 이미 준비돼 있다

2단계(Schema Retrieval)는 "모든 속성의 `rdfs:comment`를 임베딩해 둔다"를 전제한다. 실제 TTL을 세어 보면 성립한다.

fp:ratingRank  rdfs:comment

## 2. 확정 기술스택 — 임베디드 3계층


| 계층         | 엔진                                          | 선정 근거                                                                                                                                             |
| ---------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RDB**    | **DuckDB**                                  | 집계·조인·정렬에서 SQLite 대비 10~100배. CSV 직접 질의로 적재 단계가 짧다. 서버 프로세스 불필요                                                                                   |
| **Graph**  | **pyoxigraph** (SPARQL)                     | 기존 `ontology/*.ttl`을 **변환 없이** 벌크 로드. rdflib 대비 SPARQL 수십 배(터미널 노드 탐색 19.99ms vs 752.35ms). rdflib은 100만 트리플 구간에서 수십 초라 유형4의 다단계 순차 경로에서 예산을 소진한다 |
| **Vector** | **FAISS**                                   | CLOVA `bge-m3` 1024차원 cosine. 코퍼스가 1만 청크 미만이라 인덱스 구조 선택이 자유롭다                                                                                     |
| **LLM**    | HyperCLOVA X — `langchain_naver.ChatClovaX` | 과제 필수 제약. `.env`의 `clova=` 키 사용                                                                                                                   |


**신규 의존성 3개**: `duckdb`, `pyoxigraph`, `faiss-cpu`
이미 설치됨: `fastapi`, `uvicorn`, `rdflib`, `langchain`, `langchain-naver`, `pandas`, `numpy`

**임베디드를 고른 이유:** 1단계 산출물(TTL)을 그대로 재사용할 수 있고, 배포처가 미정이어도 파일 기반이라 어디에 올려도 동작한다. 다중 프로세스 동시 쓰기가 불가능하지만 평가는 단일 질의 read-only라 무관하다.

| 용도                        | 모델               | 근거                                                        |

### LLM 호출 횟수 — 1차 기획 정정

1차 기획 요약은 "합계 LLM 2회"라고 적었으나 본문의 단계 E(답변 생성)가 빠져 있다. 실제는 **3회**다.

```
1단계 Intent Classification   LLM 1회  (HCX-DASH-002, 짧은 prompt)
2단계 Schema Retrieval        LLM 0회  (벡터 검색만)
3단계 Query Planning          LLM 1회  (HCX-007, structured outputs)
   ↓ 계획 실행 — 파이썬 코드. LLM 0회
단계 E 답변 생성               LLM 1회  (HCX-007)
─────────────────────────────────────
합계                          LLM 3회 + 벡터 검색 1~2회
```

60초 예산에서 3회는 여유가 있다. 다만 유형6(TBox 검증 단독, 5건)은 **LLM 0~1회로 끝난다** — 3절 우선순위의 근거다.

## 4. 2단계 (KnowledgeBase) — 실행계획

### 4.0 디렉터리

주최측 권장 구조(과제설명 PDF p8)대로 `src/`를 신설한다. `EDA/`는 수집·빌드 스크립트 위치로 존치한다.

```
src/kb/

  build_graph.py      # ontology/*.ttl → pyoxigraph 스토어
  build_schema_index.py   # TBox rdfs:comment → FAISS  ← 1차 기획 2단계의 입력
  build_content_index.py  # 서술형 텍스트 → FAISS
  schema.py           # 3계층 공통 식별자·정규화·상수
requirements.txt      # 신규 (제출 필수)
```

### 4.1 RDB (DuckDB)

`data/csv/` 원본 4 + `data/enriched/` 5 + `data/relations/` 3 = **12테이블 1:1 적재**. 숫자 필터·정렬·집계를 전담한다(유형1의 14건 전부, 유형2~4의 정렬 구간).

- 파생·보강 컬럼은 이미 `enriched/`에 있으므로 SQL에서 재계산하지 않는다
- 출처 컬럼(`*_source`·`source`·`as_of`)을 그대로 실어 `retrieved_context` 조립에 쓴다
- `data/csv/` 동결 규칙 유지 — DuckDB는 읽기만 한다
- 유형2·3·4의 `WHERE IN` 패턴(Graph 결과 주입)을 위해 PK 인덱스를 명시적으로 만든다

### 4.2 Graph (pyoxigraph)

스키마 TTL 5 + 인스턴스 TTL 5를 **서버 기동 전 벌크 로드 1회**. 런타임 파싱 금지.

- **named graph 분리**: 스키마(TBox)와 인스턴스(ABox)를 다른 그래프에 넣어 유형6(TBox 검증 단독)이 ABox를 건드리지 않게 한다
- 국내/해외 구분은 클래스가 아니라 **인스턴스 URI 접두**(`fpi:etfkr-` / `fpi:etfgl-`)로 한다 → 정정 C4
- 유형4(다단계 순차 8건)가 응답 시간의 최대 위험 구간이다. 자주 쓰는 경로(`기업→자회사→편입종목→ETF`)는 **빌드 시점에 중간 결과를 물질화**해 홉 수를 줄인다

정정 C2~C5를 반영한 예시 SPARQL(1차 기획 단계 A의 수정본):

```sparql
SELECT ?etf ?name WHERE {
  ?etf a fp:ETF ;
       rdfs:label ?name ;
       fp:hasRiskGrade ?rg ;
       fp:leverageFactor ?lev .
  ?rg fp:riskGradeLevel ?lvl .
  FILTER (?lvl >= 5)                       # 5=낮은위험, 6=매우낮은위험
  FILTER (?lev = 1)                        # 1배 — 레버리지·인버스 제외
  FILTER (STRSTARTS(STR(?etf), "http://mafest.ai/instance/etfkr-"))
}
```

### 4.3 Vector — 2개 인덱스로 나눈다

**이것이 1차 기획을 반영한 가장 큰 설계 변경이다.** 벡터를 하나로 두면 스키마 검색과 근거 검색이 섞인다. 목적·크기·갱신 주기가 다르므로 분리한다.


|       | **스키마 인덱스**                                           | **콘텐츠 인덱스**                    |
| ----- | ----------------------------------------------------- | ------------------------------ |
| 대상    | TBox의 `rdfs:comment` + `rdfs:label` + `skos:altLabel` | 상품·기업의 서술형 텍스트                 |
| 규모    | **193 청크** (현재)                                       | 약 6천~1만 청크                     |
| 쓰는 곳  | **1차 기획 2단계** — "안전한" → `fp:riskGradeLevel`           | 단계 C — 근거 문장 보강                |
| 갱신    | TTL 수정 시 재빌드 (스크립트 1회)                                | 데이터 수집 시                       |
| 메타데이터 | `term_uri`, `domain_file`, `property_type`            | `pd_itm_no`, `source`, `as_of` |


**스키마 인덱스가 이번 2단계의 핵심 산출물이다.** 193청크뿐이라 임베딩 비용이 사실상 0이고, 근거 문서가 하나도 없는 현재 상태에서도 **즉시 동작하며 유형1·2·5·6(25건, 71.4%)을 커버**한다.

콘텐츠 인덱스 1차 코퍼스 — **신규 수집 없이 보유 데이터만** 쓴다:


| 원천                              | 규모                                      | 비고             |
| ------------------------------- | --------------------------------------- | -------------- |
| 해외ETF `cu_strtegy` (운용전략 영문 서술) | 5,646건 · 평균 309자 · 고유 5,566종            | 가장 밀도 높은 서술 필드 |
| DART 지배구조 `invest_purpose` 등    | `company_subsidiary.csv` 29,524행의 서술 부분 | 이미 보유          |
| 상품 마스터 분류명·벤치마크명                | 4도메인                                    | 의미 검색 보조       |


⚠️ `**cu_strtegy`는 해외ETF에만 있다.** 1차 기획의 예시("안전한 ETF")는 국내ETF 질의이므로 **단계 C의 근거 텍스트가 현재 존재하지 않는다.** 투자설명서 확보 전까지 국내ETF 질의의 Vector 근거는 스키마 인덱스(분류 조건의 의미 설명)로만 대체한다. 답변에서 "왜 안전한가"는 **위험등급·레버리지 분류 근거로 한정**하고, 없는 근거를 지어내지 않는다.

- 청킹: 원천 테이블·컬럼·PK·`as_of`를 메타로 붙이고 **인용 offset 보존**
- 임베딩 결과는 파일 캐시. 재빌드 시 변경분만 재계산

### 4.4 재현성

- 빌드 산출물(`.duckdb`, oxigraph 스토어, FAISS 인덱스)은 **전부 gitignore**. 빌드 스크립트만 커밋한다 (`instances_*.ttl` 선례)
- `requirements.txt` 신설: `duckdb`, `pyoxigraph`, `faiss-cpu`, `pandas`, `numpy`, `rdflib`, `requests`, `openpyxl`, `lxml`, `pyvis`, `fastapi`, `uvicorn`, `langchain`, `langchain-naver`
- 미해결 식별자(편입종목 90건, 자회사 매칭률 **행 기준 30.33%** / 고유 자회사명 기준 26.48%)는 **공란 유지 + `unresolved` 플래그**. 추가 매칭 시도 안 함(오매칭 위험) — 이 플래그를 ABSTAIN 근거로 쓴다

## 5. 3·4단계 인터페이스 — 2단계가 노출해야 하는 것

2단계는 세 계층을 세우고 **아래 4개 함수만 노출**한다. 라우팅·분해·통합은 3단계 소관이다.

```python
sql(query: str) -> list[dict]                  # DuckDB. 출처 컬럼 포함 반환
sparql(query: str) -> list[dict]               # pyoxigraph
schema_search(text, domain, k=5) -> list[dict] # 스키마 인덱스 → 1차 기획 2단계
content_search(text, filter, k=5) -> list[dict]# 콘텐츠 인덱스 → 단계 C
```

`schema_search`의 반환에는 `term_uri`와 `rdfs:comment` 원문이 반드시 포함된다. 3단계 LLM prompt에 그대로 주입되는 값이기 때문이다.

## 6. 구현 우선순위

1차 기획의 유형 분류를 커버리지 판정(`docs_data_layer/QUERY_COVERAGE_35.md` 08-16)과 교차하면 순서가 나온다.


| 순위  | 대상                       | 문항 수 | 필요한 것                          | 근거                                  |
| --- | ------------------------ | ---- | ------------------------------ | ----------------------------------- |
| 1   | **유형6** TBox 검증          | 5    | Graph(TBox) + 규칙. **LLM 0~1회** | 감점 방지 구간이고 데이터 의존이 없다. 4/5가 이미 '가능' |
| 2   | **유형1** RDB 단독           | 14   | DuckDB + 스키마 인덱스               | 전체의 40%. 9/14가 이미 '가능'              |
| 3   | **유형5** Graph 단독         | 2    | Graph(ABox)                    | 관계 존재 확인만                           |
| 4   | **유형2** Graph→RDB        | 4    | 두 계층 연결                        | `WHERE IN` 주입 패턴 확립                 |
| 5   | **유형3** Graph→RDB+Vector | 2    | 콘텐츠 인덱스                        | 병렬 실행의 유일한 실효 구간                    |
| 6   | **유형4** 다단계 순차           | 8    | 경로 물질화 + 문서 확보                 | 3건(23·25·30)은 데이터 부재로 현재 불가         |


**병렬화 판단:** 현재 데이터 기준으로 병렬이 실효인 문항은 유형3의 2건(5.7%)뿐이다. 나머지 33건은 단일 엔진이거나 순차 의존이다. `**asyncio` 도입은 유형3 착수 시점(순위 5)까지 미룬다** — 그 전에 넣으면 얻는 것 없이 디버깅만 어려워진다.
