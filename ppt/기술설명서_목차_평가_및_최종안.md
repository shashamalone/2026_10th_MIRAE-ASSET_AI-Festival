# 기술설명서 목차 평가 및 최종안

> 결론: 초안은 심사 관점을 모두 명목상 포함하지만, **baseline 대비 차별화**, **현재 구현 경계**, **전체 평가와 부분 측정의 구분**이 목차 전면에 드러나지 않는다.  
> `3. 전체 아키텍처`, `4. 제안 방법`, `6. 시스템 구성도`, `7. 주요 기능 흐름도`는 중복 가능성이 크므로 재편한다.  
> 최종안은 **문제 → baseline 비교 → 구현 구조·경계 → 신뢰성 → 정량 평가 → 운영·확장 → 한계** 순으로 확정한다.

## 1. 심사 관점별 초안 목차 평가

`audience_and_rubric`에는 실제로 6개 관점이 제시되어 있으므로, 누락 방지를 위해 1~6번 전체를 기준으로 평가한다.

| 심사 관점 | 관련 초안 섹션 | 평가 | 보완 필요 사항 |
|---|---|---|---|
| 1. 실제 금융상품 탐색 문제 정의 | 1, 2, 12 | 부분 충족 | 데이터 함정, 정형 조건 검색, 관계 검색, 문서 근거 검색이 왜 하나의 일반 문서 RAG로 해결되지 않는지 구체적인 실패 사례로 제시해야 한다. |
| 2. baseline 대비 기술적 차별화와 수치 입증 | 3, 4, 10 | 미흡 | 세 baseline을 직접 비교하는 독립 섹션이 없다. Exp5, 결정적 RDB 14문항, Graph 부분 측정을 동일한 표에서 실험 범위를 구분해 제시해야 한다. |
| 3. 환각 통제·근거 제시·미지원 질의 거절 | 5, 8, 9 | 대체로 충족 | 구현 완료 항목과 `blocking_reasons`, typed ABSTAIN 등 부분 구현 항목을 분리해야 한다. 데이터 미수집과 관계 부재를 구분하는 규칙도 명시해야 한다. |
| 4. 현재 구현과 향후 계획 구분 | 13 | 미흡 | 로드맵만으로는 현재 구현 경계가 보이지 않는다. 본문 앞부분에 상태표를 두고 모든 기능에 `구현 완료`, `부분 구현`, `실험 검증`, `설계 완료·배선 예정`, `확인 필요`를 표시해야 한다. |
| 5. 현업 적용과 상품군 확장 현실성 | 9, 11, 12, 13 | 부분 충족 | API·배포 구성의 최종 상태가 확인되지 않았다. 현재 지원 상품군, 운영 제약, 다음 상품군 확장 시 재사용되는 구성과 새로 필요한 구성을 구분해야 한다. |
| 6. 데이터·온톨로지·평가 재현성 | 5, 10, 14 | 부분 충족 | 재현 정보가 부록에 분산돼 있다. 본문에서 데이터 정본, cutoff, 실제 기준일, artifact, 테스트 기록을 요약하고 상세 명령과 매핑은 부록으로 연결해야 한다. |

### 누락 판정

제목 수준에서 완전히 빠진 심사 관점은 없다. 그러나 다음 세 관점은 현재 목차만으로는 심사위원이 구현 여부를 확신하기 어렵다.

- **관점 2:** baseline 비교가 독립적으로 드러나지 않는다.
- **관점 4:** 현재 구현과 계획의 구분이 마지막 로드맵에만 의존한다.
- **관점 6:** 재현성이 부록 항목에만 머물러 본문의 신뢰 근거가 약하다.

## 2. 3번과 4번의 중복 진단

> 결론: 두 절을 그대로 유지하면 RDB·Graph·Vector와 온톨로지가 반복 설명된다.  
> `3. 전체 아키텍처`는 **무엇이 어떻게 연결되는가**, `4. 제안 방법`은 **각 실패를 어떤 구현으로 막았는가**를 담당하도록 분리해야 한다.  
> 다만 초안의 6번과 7번까지 고려하면 부분 통합이 가장 명확하다.

### 현재 중복 지점

| 항목 | 3. 전체 아키텍처 및 특화 기능 | 4. 제안 방법 | 중복 위험 |
|---|---|---|---|
| RDB·Graph·Vector 역할 | 구성 요소로 설명 | 검색 방법론으로 재설명 | 높음 |
| 온톨로지 | Graph 구성 요소로 설명 | 온톨로지 엔지니어링으로 설명 | 높음 |
| 데이터 수집·정제 | 데이터 계층에서 언급 가능 | 독립 하위 절로 설명 | 중간 |
| 특화 기능 | 아키텍처 절에 포함 | 설계 근거로 다시 제시 | 높음 |
| 실행 흐름 | 3번에서 설명 가능 | 6번·7번에서도 반복 | 매우 높음 |

### 확정 재편안

- 초안 3번과 6번을 통합해 **「런타임 아키텍처와 구현 현황」**으로 구성한다.
  - 현재 실제 배선만 표시한다.
  - Intent 2회 호출, 결정적 Guard, 규칙 기반 Plan, 웨이브 스케줄링을 정확히 표현한다.
  - TBox Vector Grounding, 전역 Route Guard, 최대 3스텝 제한은 현재 필수 구성처럼 그리지 않는다.
- 초안 4번은 두 절로 분할한다.
  - **「데이터·온톨로지 기반과 거버넌스」**
  - **「검색 엔진별 설계와 선택 근거」**
- 초안 7번의 오프라인 흐름은 데이터·온톨로지 절로 이동한다.
  - `수집 → 검증 → 정제 → 온톨로지·관계 생성 → RDB·Graph·Vector 적재`
  - 온라인 질의 흐름과 혼합하지 않는다.
- 온라인 흐름은 **「질의 처리와 신뢰성 제어」**에서만 다룬다.
  - `Intent → 검수·보정 → Plan → Retrieval → Evidence 검증 → Answer/답변 거절`

## 5. 섹션 간 중복 처리 규칙

> 결론: 같은 사실은 한 절에서만 상세 설명하고, 다른 절에서는 판단에 필요한 한 줄과 내부 참조만 제공한다.  
> 구조·구현·신뢰성·평가를 서로 다른 질문에 답하는 절로 고정한다.

| 중복 위험 | 처리 규칙 |
|---|---|
| 문제 정의와 기대효과 | 2절은 현재 탐색 과정의 실패만 다룬다. 10절은 해당 실패가 통제됐을 때의 현업 가치만 다룬다. |
| baseline 비교와 엔진 상세 | 3절은 비교표와 차별화 결론만 제시한다. 구현 방식은 6절에서 설명한다. |
| 아키텍처와 질의 흐름 | 5절은 구성 요소·연결·현재 배선을 보여준다. 7절은 한 질의가 통과하는 검증 순서와 실패 분기만 설명한다. |
| 데이터 파이프라인과 온라인 질의 파이프라인 | 오프라인 수집·검증·적재는 4절, 온라인 검색·생성은 5절과 7절로 분리한다. |
| 온톨로지 설계와 Graph 검색 | 4절은 데이터 모델과 의미 제약을 설명한다. 6.2절은 그 제약이 계획 검증과 SPARQL 실행에 어떻게 사용되는지만 설명한다. |
| Evidence와 데이터 계보 | 4절은 provenance가 생성·보존되는 방식을 설명한다. 7절은 Evidence가 답변 허용 여부를 결정하는 방식을 설명한다. |
| 구현 상태와 로드맵 | 5.2절은 현재 시점의 상태표다. 11절은 미완료 항목의 우선순위와 완료 조건만 제시한다. |
| 성능 수치의 반복 | 모든 상세 수치는 8절에만 둔다. Executive Summary와 3절에는 판단에 필요한 대표 수치만 두고 8절을 참조한다. |
| 초기 실험과 현재 성능 | Exp2~Exp6은 `실험 검증`, 2026-09-03 결과는 `개선 전 전체 기준선`, 2026-09-05 결과는 `부분 측정`으로 고정 표기한다. |
| 15초 목표 | 모든 절에서 `목표`로만 표현한다. 최종 전체 재측정 전에는 달성·보장·SLA 준수로 표현하지 않는다. |
| 답변 거절 기능 | 구현된 일반 거절은 `구현 완료`, 표준 subtype 통합과 전역 하드 차단은 `부분 구현`으로 분리한다. |
| Vector 상태 | 콘텐츠 검색의 현재 구현과 제출 환경 적재 상태를 분리한다. TBox Vector Grounding은 필수 런타임 단계로 표시하지 않는다. |
| 확인되지 않은 정보 | 추정하지 않고 해당 절 끝에 `[확인 필요]`로 모은 뒤 A.9 제출 전 확인 목록에도 반영한다. |
