### 22번은 성격이 다르다 — 수집이 아니라 기록 문제일 수 있다

22가 요구하는 "편입내역 문서명·인용문"은 **편입 데이터를 이미 갖고 있다**(운용사 4사, 47,016행).
없는 것은 **그 데이터를 어느 문서에서 가져왔는지에 대한 기록**이다.
`etf_holding.csv` 스키마는 `source`(KODEX/TIGER/RISE/ACE)·`as_of`뿐이고 URL·문서명·조회일이 없다.

**확인 결과 — 이미 기록돼 있다.** `collect_etf_holdings.py:202-204`가 원본과 함께 사이드카를 쓴다:

```python
meta = {"source": a["source"],          # "삼성자산운용 KODEX (samsungfund.com)"  → 발행기관
        "as_of": AS_OF,                 # 2026-07-10                            → 기준일
        "retrieved_at": ...isoformat(), # 조회 시각(UTC)                          → 조회일
        "url": url,                     # 실제 엔드포인트                          → 문서 출처
        "isin": ..., "ticker": ..., "name": ...}
```

브랜드별 `source` 값도 사람이 읽을 수 있는 형태로 이미 박혀 있다 —
`삼성자산운용 KODEX (samsungfund.com)` / `Mirae Asset TIGER ETF (investments.miraeasset.com/tigeretf)` /
`KB Asset Management RISE ETF (riseetf.co.kr)` / `한국투자신탁운용 ACE ETF (papi.aceetf.co.kr)`.

→ **22번은 재수집이 필요 없다.** 문서명·발행기관·발행일 3요소가 `data/external/etf_kr_holdings/`의
`.meta.json`에 이미 있고, 남은 것은 이를 **답변 evidence로 흘려보내는 배선**뿐이다.
편입내역의 "인용 근거"는 서술 문장이 아니라 **해당 문서의 편입 행 자체**로 성립한다
(예: "삼성자산운용 KODEX 구성종목, 2026-07-10 기준 — Cambricon Technologies Corp 10.45%").

**22는 문서 수집 대상이 아니라 배선 대상이다.** 4문항 중 가장 싸다.

### 3.2 왜 DART인가 — 생존편향이 원천 차단된다

편입종목 수집 때 겪은 문제(운용사가 상장폐지 종목을 지워 과거 조회도 0행, 25종)가 **문서에서는
발생하지 않는다.** DART는 공시 **아카이브**라 접수된 서류가 사라지지 않고, `bgn_de`/`end_de`로
접수일 범위를 직접 자른다. 재수집해도 **같은 결과가 나온다** — 지금까지 확보한 외부 데이터 중
유일하게 재현 가능한 소스가 된다.

이건 부수 효과가 아니라 큰 값이다. 현재 `derivation=external` 8속성이 전부 재현 불가라
`instances_*.ttl`을 사람이 들고 다녀야 하는 상황인데, 문서 축은 그 문제를 물려받지 않는다.

## 4. 최소 몇 종을 받아야 하는가 — **AUM 상위 N은 실패한다**

국내ETF 1,202종(ETN 제외)의 순자산 집중도를 실측했다. 합계 499.4조원.

| 상위 N | 누적 순자산 | 비중 | 종목 비율 |
|---:|---:|---:|---:|
| 20 | 187.2조 | 37.5% | 1.7% |
| 50 | 279.5조 | 56.0% | 4.2% |
| 100 | 351.4조 | 70.4% | 8.3% |
| 200 | 419.5조 | 84.0% | 16.6% |
| 300 | 451.6조 | 90.4% | 25.0% |

집중도는 높다. 그런데 **문항이 요구하는 상품이 상위에 없다:**

| 문항 | 답이 되는 상품 | AUM 순위 |
|---|---|---:|
| 24 | TIGER MSCI Korea TR | **16위** ✅ |
| 22 | TIGER 차이나반도체FACTSET | **203위** |
| 22 | KODEX 차이나AI반도체TOP10 | **509위** |
| 22 | RISE 차이나AI반도체TOP4Plus | **739위** |

**상위 200종(84% AUM)을 받아도 22번의 답 3종 중 2종이 빠진다.** 순자산 집중도가 높다는 사실이
문서 수집 범위를 정해주지 못한다 — 테마·관계 질의는 소형 상품을 지목하기 때문이다.

### 권고: 질의 지향 + 얇은 광역의 2층

| 층 | 대상 | 규모 | 목적 |
|---|---|---:|---|
| **1층 (깊이)** | 문항 22·24·27·28이 답으로 제시할 상품 | **15~20종** | 4문항 확실히 커버 |
| **2층 (넓이)** | 순자산 상위 100종 | 100종 | 비공개 평가문항 대비 (70% AUM) |

합계 **120종 내외**다. 1,202종 전량 대비 10%이고, ETF 1종당 투자설명서 1건 + 자산운용보고서
소수라면 **문서 수백 건 규모**로 DART API 일일 한도 안에서 처리된다.

**1층이 먼저다.** 2층은 보험이고, 1층 없이 2층만 하면 4문항이 그대로 막힌다.

25번(국민성장펀드)은 ETF가 아니라 **정책자료 1건**이므로 이 계산 밖이다. 금융위·기재부
보도자료 계열이라 DART가 아닌 별도 경로이며, **가장 싸고 효과가 확실한 단건**이다.

## 5. 4요소 매핑 — API 필드 대응

DART 공시검색 `list.json` (문서 스펙 확인 완료):

| 근거 요소 | API 필드 | 비고 |
|---|---|---|
| 문서명 | `report_nm` | 보고서명 |
| 발행기관 | `flr_nm` | 공시 제출인명 (= 운용사) |
| 발행일 | `rcept_dt` | 접수일자 |
| 인용문 | `rcept_no` → 공시서류원본파일 API | ZIP(binary) 응답, 내부 XML |

요청 파라미터: `crtfc_key`·`corp_code`·`bgn_de`·`end_de`·`pblntf_ty`·`page_no`·`page_count` 등.
**`pblntf_ty=G`가 펀드공시**이고, 원본파일 API는 `crtfc_key`+`rcept_no` 2개만 받는다.

즉 **앞 3요소는 검색 응답만으로 채워지고, 인용문 하나만 원문 파싱이 필요하다.**

## 6. 미검증 — 그리고 이걸 닫으려면 무엇이 필요한가

**DART 인증키가 이 머신에 없다.** `collect_dart.py:7`은 `.env`의 `dart=`를 읽는데
`2026_10th_MIRAE-ASSET_AI-Festival/.env`가 존재하지 않고 `backend/.env`에도 없다.
`data/`·`instances_*.ttl`과 같은 부류의 결손이다.

따라서 **실물 1종을 열어 확인하는 검증(요청 4번)은 못 했다.** 남은 미검증 항목:

1. 특정 ETF의 투자설명서가 `pblntf_ty=G` 검색에 실제로 잡히는가
2. 원본파일 ZIP에서 **인용 가능한 문장**이 뽑히는가 (표·이미지가 아니라 텍스트인가)
3. "위험요인" 섹션이 문서 내에서 안정적으로 식별되는가
4. 문항 22가 실제로 재수집 없이 해결되는가 (`collect_etf_holdings.py` 사이드카에 URL·조회일이 남아 있는가)

**필요한 것: DART 키 1개.** 키가 들어오면 1~3번은 API 호출 몇 번으로 닫힌다.
4번은 키 없이도 `collect_etf_holdings.py` 소스만 보면 확인되므로 **먼저 확인할 것**.
